# Installing it

One static binary, no dependencies, nothing to configure, and no daemon. Pick
whichever of these fits how the machine is managed.

> **Which releases these work for.** The archives, the checksums, the
> attestations, the Homebrew formula and the image are all produced by the
> release workflow added in EM-22. The releases before it carry none of them —
> `v0.1.0` was tagged earlier and has source only. Set `v` to a release at or
> after the first one the pipeline built, which the
> [releases page](https://github.com/Allan-Nava/edgemix/releases) lists.

| Way | Command | Version it reports | Good for |
|---|---|---|---|
| Homebrew | `brew install .../releases/download/v$v/edgemix.rb` | the released one | a laptop |
| Docker | `docker run --rm -v /var/log:/logs:ro ghcr.io/allan-nava/edgemix:v$v analyze /logs/edge.log` | the released one | a host you would rather not install anything on |
| Release archive | download, verify, `install -m755 edgemix /usr/local/bin/` | the released one | a server, an image build, an air-gapped box |
| From source | `go install github.com/Allan-Nava/edgemix/cmd/edgemix@latest` | `dev` | following main |

## Homebrew

```bash
v=0.2.0   # a release built by the pipeline; see the note above
brew install "https://github.com/Allan-Nava/edgemix/releases/download/v$v/edgemix.rb"
```

The formula is **generated by the release run** that built the archives —
`scripts/brew.sh` reads the checksums out of the `SHA256SUMS` it just produced —
and attached to the release. A checksum a person typed is one that is wrong the
first time an archive is rebuilt, and Homebrew's failure for that looks like a
network problem.

Two things this does not do, both worth knowing before you pick it:

- **`brew upgrade` will not find a new version.** Installing from a URL pins
  that formula; upgrading means installing the next release's URL. A tap is what
  makes `brew upgrade` work, and there is not one yet — that is [EM-43](https://github.com/Allan-Nava/edgemix/blob/main/BACKLOG.md)
  in the backlog.
- **edgemix cannot go into `homebrew-core`.** Core takes open-source licences
  only, and this is [PolyForm Noncommercial](https://github.com/Allan-Nava/edgemix/blob/main/LICENSE).
  That is a licensing fact rather than an oversight.

The formula's own `brew test` runs two assertions: that the binary reports the
version the formula claims, and that it reads a two-line log and says the peak
was 2 req/s. The second one exists because a test that only checks the binary
starts is a test that passes on an empty file.

## Docker

```bash
docker run --rm -v /var/log:/logs:ro ghcr.io/allan-nava/edgemix:v0.2.0 \
  analyze /logs/haproxy-edge.log
```

The image is the binary and nothing else: `FROM scratch`, **2.4 MB**, no shell,
no CA bundle, no resolver, running as `65534:65534`. edgemix reads files and
makes no network calls, so none of that is missing — it was never needed. A
container that can only run one program is one less thing to reason about when
it is pointed at a copy of production logs.

If a pull fails with `unauthorized` or `denied`, the package is still private:
a container image pushed by a workflow token starts that way, and its visibility
has to be flipped once by hand on GitHub. That is a setting on the package, not
something wrong with the command.

`:latest` follows the newest release; a version tag is what belongs in a script
or a CI job, because a report is only comparable with another one from the same
binary.

Mount the logs **read-only**. It never writes to them, and `:ro` is how you
know that without reading this page.

A pipe works too, with `-i`:

```bash
ssh lb1 'tail -n 200000 /var/log/haproxy.log' |
  docker run -i --rm ghcr.io/allan-nava/edgemix:v0.2.0 analyze --dialect haproxy -
```

To write a profile out, mount somewhere writable and point `-o` at it:

```bash
docker run --rm -v /var/log:/logs:ro -v "$PWD:/out" ghcr.io/allan-nava/edgemix:v0.2.0 \
  profile --base-url https://www.example.test /logs/edge.log -o /out/profile.json
```

Because there is no shell in the image, `docker exec` and `docker run … sh` do
not work. That is the trade for the size and the surface; the binary's own
`--help` is the only interface it has.

## Release archive

Six archives per release — Linux, macOS and Windows, on `amd64` and `arm64` —
each with its checksum in `SHA256SUMS`:

```bash
v=0.2.0
base=https://github.com/Allan-Nava/edgemix/releases/download/v$v
curl -fLO $base/edgemix_${v}_linux_amd64.tar.gz
curl -fLO $base/SHA256SUMS
sha256sum --check --ignore-missing SHA256SUMS
tar -xzf edgemix_${v}_linux_amd64.tar.gz
sudo install -m755 edgemix /usr/local/bin/edgemix
```

A checksum says the archive is the one the release published. It does not say
who built it, which is why every archive also carries a **sigstore provenance
attestation** — generated by the release workflow, with no key for anybody to
lose:

```bash
gh attestation verify edgemix_${v}_linux_amd64.tar.gz --repo Allan-Nava/edgemix
```

That tells you the file was built by that repository's release workflow, from a
named commit. The image carries the same attestation, pushed to the registry
beside it.

## From source

```bash
go install github.com/Allan-Nava/edgemix/cmd/edgemix@latest
```

`go install` sets no linker flags, so the binary reports its version as `dev`
rather than a number. That is honest — it is whatever `main` was at the time —
but it means a report from it cannot be attributed to a release. Use a release
archive when the report is going into a ticket.

Building the repository yourself gives the same thing with a version:

```bash
git clone https://github.com/Allan-Nava/edgemix && cd edgemix
go build -ldflags "-X main.version=$(git describe --tags --always)" -o edgemix ./cmd/edgemix
```

There is nothing to fetch: `go.mod` has no `require` block, and CI fails the
build if one appears.

## What none of these install

No daemon, no service file, no config file, no state directory, and no network
listener. edgemix runs, reads the files it was given, writes a report to stdout
or to `-o`, and exits. That is the whole of it, and it is what makes it safe to
point at a copy of production logs.
